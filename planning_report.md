# BashaLagbe: Planning & Architecture Report

## 1. Current Project Status & Architecture
The BashaLagbe project is currently a Flutter-based Android application integrated with Firebase (Authentication, Firestore, Cloud Functions, and Storage via Cloudinary).
*   **Flutter UI:** A fully functional discovery UI exists with bottom navigation (Home, Saved, Post, Profile). It includes searching, filtering (Bachelor, Family, Shared), property detail views, user profile management, and a robust "Post Property" wizard. The UI adheres to a calm, premium design system (Forest Green `#244B3B`, Warm Ivory `#F7F4EC`).
*   **Firebase Integration:** The project actively uses Firebase Auth, Firestore, and Cloud Functions.
*   **Firestore Data Model:** Exists for `users`, `properties`, `rental_requests`, `contact_info` (subcollection to protect privacy), `conversations`, `messages`, and `media_cleanup_tasks`. Security rules are thoroughly implemented, ensuring strict read/write access (e.g., only authenticated users can post, landlords can manage their listings, only participants can read/write to chat, and admin actions are secure).
*   **Media Handling:** Photos are uploaded to Cloudinary, orchestrated via signed uploads generated by Firebase Cloud Functions. A robust background `media_cleanup_tasks` system ensures deleted listings remove associated photos securely and idempotently.
*   **Moderation & Status:** Property listings have a `pending`, `approved`, or `rejected` state. Modifying a property automatically resets its state to `pending`.

**What is working:** User authentication, saving favorites, posting property listings, photo uploads/deletions, rental requests, real-time messaging, and strong security boundaries.
**What is incomplete/missing:** External property integrations (hotel/resort APIs), unified "My Stays", direct bookings, payments, and admin dashboards (though server-side roles exist).

## 2. Preserving Existing Features
*   **Visual Identity & Theming:** The existing color palette (Forest Green, Warm Ivory) and typography (Inter with Bangla fallbacks) are well-implemented and should be retained.
*   **Core Navigation & Component Structure:** The current shell and navigation (`MainShell`), property cards (`PropertyCard`), and screen layouts (`HomeScreen`, `SavedScreen`, etc.) should be expanded rather than rewritten.
*   **Current Security Posture:** The robust Firestore security rules (`firestore.rules`) and Cloud Functions for secure media cleanup must be preserved and carefully augmented, never weakened.
*   **Separation of Concerns:** The existing `FirestoreService` and `AuthService` should remain the central points of interaction with Firebase.

## 3. Risk Assessment, Bugs, and Architectural Gaps
*   **Technical Debt / Gaps:** The data model heavily favors long-term rentals (`rentPerMonth`). It lacks fields for short-term stays (nightly rates, availability calendars).
*   **Security Risks:** While current rules are strong, introducing payments and direct bookings will significantly expand the attack surface. Double bookings must be prevented server-side via atomic transactions.
*   **Dependency / Cost Risks:** Relying on Cloudinary and Firebase could lead to high costs at scale. Cloudinary usage needs close monitoring.
*   **External Integration Risks:** No external API (Booking.com, GoZayaan, etc.) is currently integrated. Availability of these APIs for Bangladesh, their terms of service, and technical feasibility remain unverified.

## 4. Recommended Product Architecture & Data Model Direction
To support the Hybrid Marketplace, the `properties` collection schema needs adjusting to support multiple accommodation types natively while distinguishing between *Owner-Managed* and *External Discovery* listings.

*   **Unified Schema Updates:**
    *   Introduce `listingSource`: `internal` (owner-managed) vs `external` (API/affiliate).
    *   Introduce `pricingModel`: `monthly` (rentals) vs `nightly` (hotels/resorts).
    *   Introduce `externalSourceData`: A map containing `providerName`, `providerUrl`, `lastCheckedTimestamp`, and `externalId`.
    *   Introduce `bookingType`: `request_to_rent`, `instant_book`, `external_redirect`.

## 5. External Discovery Strategy & Compliant Source Options
We will not scrape data. We will rely entirely on authorized feeds, official APIs, or affiliate networks.
*   **Immediate Action:** Research available affiliate programs for Bangladesh accommodations (e.g., Booking.com Affiliate Partner program, Agoda, local OTAs if they offer APIs).
*   **Implementation:**
    *   External listings will be fetched and stored/cached in Firestore (if ToS allows) or fetched via Cloud Functions on the fly.
    *   UI must prominently display: "Sourced from [Provider]" and a "Last checked: [Time]" label.
    *   Clicking "Book" will show the mandated confirmation dialog: *"You're continuing to an external booking provider..."* before opening the deeplink.

## 6. User, Partner, and Admin Permission Model
The existing model separates users and admins (`/admins/{userId}`). We will expand this:
*   **Regular User:** Can search, save, request rentals, chat, and eventually book directly.
*   **Partner (Owner-Managed):** Regular users who have completed a "Partner Verification" workflow. They gain access to a "Partner Dashboard" to manage inventory, nightly rates, and accept bookings. (Verification status can be a field on the user profile or a separate `/partners/{userId}` collection).
*   **Administrator:** Maintained securely in `/admins`. Will require a web-based or responsive Flutter dashboard to moderate listings, verify partners, handle disputes, and oversee external data freshness.

## 7. Proposed Navigation and Elegant UX Improvements
*   **Current:** Home, Saved, Post, Profile.
*   **Proposed Evolution:**
    *   **Home:** Unified search. Add a top tab or contextual filter for "Long-term Rentals" vs "Short-term Stays" to declutter filters.
    *   **Saved:** Remains as is, but groups by rentals vs. travel.
    *   **My Stays:** Replaces "Post" for regular users. Shows upcoming trips, pending rental requests, and past stays.
    *   **Partner/Host Hub:** A dedicated section accessible via Profile (or replacing "My Stays" if the user is an active partner) to manage properties and bookings.
    *   **Profile/Inbox:** Consolidates chat and account settings.

## 8. Direct-Booking and Payment Strategy
*   **Architecture:** Direct bookings will require a new `bookings` collection. Bookings must be created via Cloud Functions to enforce atomic checks against an `inventory` or `availability` subcollection, preventing double-bookings.
*   **Payment:** We will start with a **"Reserve now, pay at property"** model to avoid payment gateway complexities initially.
*   **Online Payments (Future):** Integration with a local payment gateway (e.g., SSLCommerz, bKash API, aamarPay). This requires a registered business entity in Bangladesh, merchant accounts, and strict webhook verification via Cloud Functions. Never process payments client-side.

## 9. Phased Roadmap
*   **Phase 0 — Audit & Foundation:** (Current phase) Review, plan, and secure the foundation.
*   **Phase 1 — Stable Rental Marketplace (Refinement):** Polish the existing Flutter app, fix any lingering bugs in the rental request/chat flow, and launch the core long-term rental feature.
*   **Phase 2 — Compliant External Discovery:** Research APIs, implement external listing UI components (disclaimers, deeplinks), and integrate the first authorized feed for hotels/resorts.
*   **Phase 3 — Partner Onboarding & "My Stays":** Build the partner verification workflow, adapt the listing wizard for short-term stays, and implement the unified "My Stays" UI.
*   **Phase 4 — Controlled Direct-Booking Pilot:** Implement the backend booking engine (atomic transactions, double-booking prevention) using the "Pay at Property" model with a select few verified partners.
*   **Phase 5 — Booking Payments & Guest Services:** Integrate a local payment gateway, handle refunds/cancellations, and add in-stay service ordering.
*   **Phase 6 — Growth & Differentiation:** Price-drop alerts, maps, verified reviews, and personalized recommendations.

## 10. Third-Party Approvals, Operational Requirements, and Cost Risks
*   **Approvals:** Must apply for OTA affiliate programs (Booking.com, Agoda). Must register a business to access local payment gateways (SSLCommerz, bKash).
*   **Costs:** Firebase (Firestore reads/writes, Cloud Function invocations) and Cloudinary (image transformations and bandwidth). As external listings grow, caching strategies will be critical to minimize Firestore read costs.
*   **Legal:** Ensure compliance with local consumer protection laws regarding pricing transparency and refunds.

## 11. Testing and Security Validation Plan
*   **Firestore Rules:** Write automated tests using `@firebase/rules-unit-testing` to verify that external listings cannot be claimed, and bookings can only be modified by authorized parties.
*   **Unit/Widget Tests (Flutter):** Test the new UI components (external disclaimers, new filter chips) and state management.
*   **Integration Tests:** End-to-end testing of the "Request to Rent" and future "Direct Booking" flows.
*   **Concurrency Testing:** Specifically test Cloud Functions handling concurrent booking requests for the same dates to ensure the atomic transaction logic holds up.

## 12. First Small, High-Value Implementation Milestone
**Milestone Proposal:** *Schema Foundation & External Listing UI Preparation.*
Before diving into complex API integrations or bookings, we should lay the groundwork in the app safely.
1.  **Data Model Update:** Update the Flutter `Property` model and `FirestoreService` to support `listingSource` (internal vs external), `pricingModel` (monthly vs nightly), and `externalSourceData`.
2.  **UI Adaptation:** Modify `PropertyCard` and `PropertyDetailsScreen` to gracefully handle and display external listings. If a property is external, it should display the "Sourced from..." badge, hide the "Request Rent" button, and show an "External Booking" button that triggers the mandated confirmation dialog.
3.  **Validation:** Create a mock external listing in Firestore manually to test the UI changes without writing scraper/API code yet.
